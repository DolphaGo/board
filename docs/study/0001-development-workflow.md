## 요구사항과 완료 조건

게시판 기능을 하나씩 PR로 올리고, 개념과 구현 방법을 공부할 수 있게 기록한다. 이번 작업은 이 방식을 저장소 규칙과 문서로 정착시키는 문서 PR이다.

- 기능 하나의 요구사항·개념·코드·검증을 같은 PR에서 읽을 수 있는 양식이 있다.
- 현재 코드에서 공부할 지점과 다음 PR 후보를 찾을 수 있다.
- README에서 학습 가이드와 첫 기록으로 이동할 수 있다.
- 애플리케이션 동작은 이번 범위에 포함하지 않는다.

## 개념과 선택 이유

**Commit**은 파일 변경을 기록하는 단위이고, **branch**는 작업 이력을 가리키는 이름이다. 기능별 브랜치를 쓰면 서로 다른 기능의 변경을 구분해 리뷰할 수 있다. 작은 논리 단위로 변경을 나누면 나중에 원인을 추적하기도 쉽다. [Git workflow 공식 문서](https://git-scm.com/docs/gitworkflows)

**Pull Request**는 작업 브랜치(head)의 변경을 대상 브랜치(base)에 합치자고 제안하는 GitHub의 리뷰 단위다. 여러 커밋, 설명, 리뷰, 검사 결과가 모인다. PR 공개와 병합은 별개의 상태이므로, PR을 올렸다고 통합이 끝난 것은 아니다. [GitHub Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)

**Worktree**는 같은 저장소의 이력을 공유하면서 별도 폴더에서 작업할 수 있게 한다. 이번에는 기존 작업 폴더의 미추적 파일을 보존하며 문서만 커밋하려고 별도 worktree를 썼다. 폴더 분리는 외부 서비스나 DB까지 분리해 주지는 않는다. [Git worktree 공식 문서](https://git-scm.com/docs/git-worktree)

**학습 기록과 PR 본문**은 역할이 다르다. 저장소 문서에는 개념·구현 과정·검증을 오래 남기고, PR에는 변경 목적과 리뷰에 필요한 요약 및 문서 링크를 둔다. 전체 설명을 양쪽에 중복하면 수정할 때 어긋나기 쉬워 이 구조를 선택했다.

## 구현 순서와 코드 읽기

1. 현재 원격 기본 브랜치와 변경 파일을 확인했다. `origin/master`를 포함해 fetch했고, 현재 기본 브랜치인 `origin/develop`을 기준으로 작업했다.
2. [AGENTS.md](../../AGENTS.md)에 다음 작업에서도 지킬 기능별 PR·학습 기록 규칙을 추가했다.
3. [학습 가이드](../STUDY_GUIDE.md)에 개념 안내, 코드 진입점, 다음 PR 후보와 복사용 기록 양식을 넣었다.
4. [PR 양식](../../.github/pull_request_template.md)에 학습 기록과 실제 검증 결과를 연결하도록 했다.
5. [README](../../README.md)와 [design.md](../../design.md)에 이 작업 방식으로 진입할 링크를 추가했다.

## 검증

이번 변경은 문서만 다룬다. 애플리케이션 테스트·빌드·실제 인프라 검증은 실행 대상이 아니다.

| 확인 | 방법 | 결과 |
| --- | --- | --- |
| 원격 기준 | `git fetch origin --prune`, 기본 브랜치 조회 | `develop`; `origin/master`가 `origin/develop`의 조상임을 확인 |
| 변경 범위 | `git diff --cached --name-only` | 문서 6개만 포함 |
| 공백 오류 | `git diff --cached --check` | 통과 |
| 로컬 문서 링크 | 추가·수정한 문서에서 코드 블록과 외부 URL을 제외하고 상대 링크 대상 파일 존재 확인 | 38개 모두 존재 |
| 내용 검토 | 요구사항, 실제 경로, fixture/실제 연동 구분을 별도 검토 | 사용자 선택을 반영해 목록 → 상세 → 글쓰기를 각각 독립 PR로 수정 |

원격 CI 상태는 PR의 Checks에서 확인한다. 현재 CI는 Jib 이미지 빌드·게시이며, 문서 검토나 애플리케이션 전체 테스트를 대신하지 않는다.

## 실패와 해결

문서 작성 중 기능 오류를 재현하거나 수정하지 않았다. 기존 README의 실행 안내와 코드 구조를 바탕으로 기록 방식을 추가했다.

## 남은 한계와 복습

- 기존 모든 기능의 상세 해설을 소급 작성한 것은 아니다. 개념 안내에서 시작해 각 기능을 다루는 PR에서 실제 코드와 검증을 붙인다.
- 다음 기능 순서는 사용자 선택에 따라 목록 → 상세 → 글쓰기로 확정했다. 각각 별도 PR로 다루며, fixture/실제 API 구분은 해당 단계의 연동 검증에 필요한 범위로 진행한다.
- 기능 PR에는 해당 변경의 구체적인 실패·경계 조건이 필요하다. 양식을 채우는 것만으로 기능 완성을 증명할 수 없다.
